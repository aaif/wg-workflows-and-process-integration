## Objective of this document

This document is a reference for finding real, working examples of agent workflows, from your own industry or others facing a similar coordination problem. Each row has enough structure (trigger, HITL gate, agent count, coordination mechanism, workflow shape, failure mode, preconditions) to be useful on its own.

### What this document is, and is not

This document is an **inventory**, not an exhaustive catalogue. It aims for breadth of *pattern* coverage across industries, not completeness within any one.

The inventory is intended to:

- Give the WG a shared, concrete set of use cases to reason about for its deliverables
- Surface the diversity of workflow patterns (trigger types, HITL patterns, agent counts, coordination mechanisms) across industries and contexts
- Provide a community-editable reference that WG members and contributors can challenge, extend, and correct

The inventory is **not**:

- A ranked or tiered list
- A recommendation of which use cases the WG should use as reference scenarios
- A statement of relative importance across categories or industries

## Assumptions and editorial decisions

This section documents the judgment calls behind this inventory. For how dimensions are defined and classified, see the [Classification Schema](./classification-schema.md) file. Read both before adding or editing rows, and flag disagreement with existing assumptions in your contribution comment.

### Scope

- **Workflow-level, not model-level.** This landscape documents *what the agent does and how it coordinates*, not how the underlying model works. Use cases were selected because they illustrate meaningful workflow primitives: tool invocation, HITL patterns, state handoffs.
- **Enterprise contexts were the primary lens.** The WG charter prioritises enterprise adoption, so use cases were sourced with enterprise deployment in mind. Consumer-facing variants of the same pattern (e.g. personal finance vs. corporate FP&A) are underrepresented as a result, a known gap rather than an intentional exclusion. Contributions covering consumer contexts are welcome.
- **Production-plausible at time of writing.** Use cases were included where at least one named organisation or published reference was deploying something similar in production or active pilot. This bar was applied unevenly across categories: evidence is easier to find for some domains (sales, engineering) than others (education, real estate). Where evidence was thinner, use cases were included if the workflow pattern was clearly viable given available tooling.
- **One row per meaningfully distinct workflow.** Where two use cases within a category shared nearly identical tool coordination and HITL patterns, they were merged or one was excluded. The intent is breadth of *patterns*, not an exhaustive list of every possible task. Which patterns are truly distinct across categories hasn't been formally analysed yet. That work belongs to the Workflow Taxonomy deliverable.

### Tools and systems

- **Named products are illustrative, not prescriptive.** Specific vendors (e.g. Salesforce, Epic, Jira) are examples of the system *type* required. The workflow pattern applies regardless of which vendor is used. Contributors should not add or remove tools based on vendor preference.
- **LLMs are not listed as tools.** Every use case assumes an LLM as the core reasoning component. Only external systems the agent must call (APIs, databases, messaging platforms) are listed in the Tools column.
- **Read vs. write access is noted where the direction creates meaningful risk.** For systems where agent write-back could cause harm or is irreversible (e.g. EHR write, financial system write, email send), the access direction is specified. Where it is obvious from context, it is omitted.

### What is out of scope for this table

The following topics are handled by other WGs and should not be added as columns or use case criteria here:

- **Observability and tracing** → Observability WG
- **Security and adversarial robustness** (prompt injection, data exfiltration) → Security WG
- **Model accuracy and hallucination rates** → Accuracy & Reliability WG. Failure modes in this table describe *workflow-level* failures (wrong routing, missed escalation, incorrect write-back), not model-level failures.
- **Regulatory and jurisdiction-specific compliance** (HIPAA, EU AI Act) → Governance & Risk WG
- **Prompt engineering** → deferred to other technical groups per the charter

### Known gaps

This table has known gaps: coverage that's thin, columns that aren't fully backfilled, and open taxonomy questions for other WG deliverables. These are tracked as a GitHub issue on this file in the parent repo, kept current as gaps close and new ones surface. See the open issues for this file, or search "known gaps" in the repo. Contributions closing any of them are welcome. See How to Contribute below.

Two categories of gap are tracked directly in the table, since they're per-row and self-documenting: cells marked **Unspecified: insufficient source detail**, and cells carrying a footnote marker for undocumented rationale. See the [Classification Schema](./classification-schema.md) file's "Classifying a row" section for what each means and how to close it.

## How to Contribute

This document is a living reference. For the general contribution process (branching, pull requests, review), see the [repo's How to Contribute guide](../CONTRIBUTING.md). The reference below is specific to this file. For the classification dimensions themselves (Trigger, HITL Pattern, Agent Count, Coordination, Workflow Pattern), see the [Classification Schema](./classification-schema.md), so new or edited rows stay consistent with the rest of the table.

### Row template

Copy this into the appropriate category table and fill in each field:

```
| **Use case name** | One or two sentence description of what the agent does. | • Tool one<br>• Tool two<br>• Tool three | `Trigger` | `HITL Pattern` | `Agent Count` | `Coordination` | `Workflow Pattern` | `Duration` | _Key failure mode description_ | What must be true beforehand for this to be safe to run. | Reference examples, source links, classification rationale or caveats. |
```

### Guidelines

- **Use case names** should be specific enough to distinguish from similar workflows (e.g. "Invoice processing & coding" not just "Finance automation")
- **Descriptions** should follow the pattern: *On [trigger], the agent [does X], [does Y], and [produces Z].*
- **Tools** should name the system type first, with a specific example in brackets where helpful (e.g. `EHR API (Epic / Cerner)`)
- **Failure modes** should describe a concrete harm, not just a vague error (e.g. "Drug interaction not flagged; patient safety event" not "agent makes a mistake")
- **Classification columns** (Trigger, HITL Pattern, Agent Count, Coordination, Workflow Pattern) follow the definitions and conventions in the [Classification Schema](./classification-schema.md) file, including how to document rationale and how to flag insufficient source detail.
